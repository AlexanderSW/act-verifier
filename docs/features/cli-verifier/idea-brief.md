# Idea brief — cli-verifier

## 1. Raw idea

Власник обрав варіант інтерв'ю: «Етап 1: CLI-верифікатор» — «Ядро з README «План реалізації»: loaders → checks C01–C13 → Excel-звіт із блоком доказів → CLI з кодами виходу 0/1/2. Зараз це заглушки, сценарії в xfail.»

## 2. Problem

Зараз ядро верифікатора — заглушки: `load_contract`/`load_act`, `verify`, `write_excel`/`render_evidence`/`append_error_log` і `main` кидають `NotImplementedError`; усі 14 сценаріїв у `tests/test_verifier.py` позначені `xfail` (source-verified: `src/act_verifier/*.py`, `tests/test_verifier.py:16`). Отже, акт неможливо перевірити ні з CLI, ні з тестів.

Бажаний результат (owner-reported): навчальний / демо-проєкт «з запасом під реальні акти» — CLI читає файли у форматі з README, виконує C01–C13 з `docs/checks.md` і видає звіт із блоком доказів. Критерій приймання — усі 14 фікстур зелені (не xfail) і `test_fixtures_integrity.py` зелений (узгоджено з CLAUDE.md, розділ «Як перевіряти свою роботу»).

«Запас під реальні акти» (owner-reported) означає: лоадер не хардкодить номери рядків — шукає рядок заголовків за текстом («Шифр», «Кількість»), а рядки підсумків — за мітками «Разом без ПДВ», «ПДВ 20%», «Всього з ПДВ». Невідома розкладка → зрозуміла помилка, а не тихий збій.

## 3. Users

- Власник проєкту — розробник і перший користувач CLI на синтетичному наборі (owner-reported).
- Рецензент роботодавця — побачить проєкт і, ймовірно, дасть реальні акти в тестовому завданні (owner-reported, що реальні акти з'являться саме там; хто саме запускатиме CLI — assumption).
- Ланцюжок із README: агент готує акт → верифікатор перевіряє → людина приймає рішення (source-verified: `README.md`, вступ). Окремого агента, що генерує акти, у репозиторії немає (source-verified: дерево файлів).

## 4. Why now

Тригер (owner-reported): реальні акти з'являться в тестовому завданні роботодавця; до того потрібне робоче ядро, яке не зламається на іншій розкладці файлу. Конкретної дати не названо — дедлайн не встановлено.

## 5. Out of scope

- Реальні акти — поза обсягом зараз (owner-reported); з'являться на тестовому завданні.
- Етап 2, `mcp_server.py` (`verify_act` як інструмент для Claude) — README, «План реалізації», крок 5, і докстрінг модуля прямо відносять його до етапу 2 (source-verified).
- Обмеження, які треба зберегти (source-verified: `CLAUDE.md`): гроші й обсяги лише `Decimal`; числа лише з файлів; бракує даних → `unknown`, ніколи `pass`; `expected.json` і xlsx у фікстурах змінюються тільки через `scripts/generate_fixtures.py`; верифікатор не записує у вхідні файли; кожен звіт закінчується блоком доказів.
- Формат входу — розкладка з README, розділ «Формат вхідних файлів» (owner-reported як обсяг).
- «Наступні сценарії» з `docs/checks.md` — число текстом («1 250,50»), нерозривний дефіс у шифрі, нульова кількість, C13 `fail` — поза етапом 1 (owner decision). Виняток: «Разом» не одразу після таблиці входить до нових фікстур розкладки (див. §7).
- Журнал `journal/agent_errors.csv` за замовчуванням не пишеться — лише з явним прапорцем (owner decision).

## 6. Risks

1. **Найслабше місце: «запас під реальні акти» досі перевіряють лише синтетичні варіанти розкладки.** Нові фікстури моделюють те, як ми уявляємо собі реальні відхилення, а не справжні акти роботодавця (assumption). Наслідок: на тестовому завданні лоадер може натрапити на розкладку, якої немає в жодній фікстурі. Це прийнято свідомо: реальні акти поза обсягом. Пом'якшення — зрозуміла помилка з окремим кодом виходу замість тихого збою. Рішення оборотне.
2. **Фікстура «невідома розкладка → помилка» не вписується в поточну схему еталону.** `test_expected_json_schema` вимагає `expected_verdict ∈ {pass, fail, needs_review}`, а `test_scenario` завжди викликає `verify` (source-verified: `tests/test_fixtures_integrity.py:31`, `tests/test_verifier.py:16-31`). Сценарій з очікуваною помилкою потребує розширення схеми й тестів. Фікстури зі зсунутою, але валідною розкладкою вписуються без змін.
3. **Мітки в реальних файлах можуть не збігатися дослівно.** Заголовок колонки в акті — «Шифр позиції за договором», у договорі — «Шифр»; кількість: «Кількість» в акті, «Кількість за договором» у договорі (source-verified: `scripts/generate_fixtures.py:38-46, 161-162`). Отже, пошук за точним збігом з README не спрацює навіть на фікстурах. Мітка «ПДВ 20%» містить ставку, і в реальних актах вона може бути іншою (assumption).
4. **Колізія кодів виходу.** `argparse` при помилці аргументів виходить із кодом 2, тим самим, що й `needs_review` (source-verified: `src/act_verifier/cli.py:18-25`; поведінка argparse — загальновідома, не перевірялась у цій сесії). Вирішено: окремий код для «вхід не прочитано», помилки виклику теж не мають давати 2 (owner decision).
5. **Журнал відстежується в git.** `git ls-files` показує `journal/agent_errors.csv`, і `.gitignore` його не виключає (source-verified: `.gitignore` у HEAD `4ad4ea2`). Кожне дописування змінює закомічений файл, тож робоче дерево стає «брудним». Пом'якшено рішенням «лише за прапорцем». Під час інтерв'ю питання помилково стверджувало, що файл підпадає під шаблон `.gitignore`. Рішення власника спиралося й на інші причини (засмічення від запусків на фікстурах, `found_by`/`resolution`), тож виправлення факту його не змінює. Проте власник має це підтвердити (§8).

Критика: проведена в цьому інтерв'ю, без незалежного агента. Підстава: зміни оборотні, нові доступи, дані чи публічні контракти поза репозиторієм не з'являються. Зовнішнє дослідження не проводилось: факти, від яких залежали рішення, є в репозиторії.

## 7. Recommendation

**Напрям (owner-accepted, 2026-11-25):** реалізувати етап 1 з README «План реалізації», кроки 1–4:

- лоадери шукають рядок заголовків і рядки підсумків за текстовими мітками;
- `verify` виконує C01–C13 за `docs/checks.md`, з правилами пропуску;
- Excel-звіт і блок доказів;
- CLI з кодами 0 = pass, 1 = fail, 2 = needs_review і окремим кодом «вхід не прочитано / помилка виклику»;
- журнал помилок пишеться лише за явним прапорцем (`found_by` = верифікатор, `resolution` порожнє).

**Спостережуваний результат:** `pytest -q` дає зелені 14 наявних сценаріїв (не xfail) і `test_fixtures_integrity.py`. Додатково зелені 2–3 нові фікстури розкладки, згенеровані через `scripts/generate_fixtures.py` з поясненням, навіщо їх додано: зсунутий заголовок, «Разом» не одразу після таблиці, відсутня мітка → помилка з окремим кодом. CLI на `data/synthetic/` дає звіт із блоком доказів.

**Головний компроміс:** нові фікстури розширюють обсяг (генератор + розширення схеми еталону для очікуваної помилки). Натомість вимога «запасу» стає перевірюваною, а не лише декларованою.

**Відхилені альтернативи:**

- лише 14 фікстур — тоді «запас» нічого не перевіряє, бо захардкожений рядок 8 теж пройде;
- юніт-тести лоадера з `tmp_path` — варіанти розкладки жили б поза єдиним джерелом правди `generate_fixtures.py`;
- звести помилку входу до коду 2 — «не перевірено взагалі» злилося б із «перевірено, є unknown»;
- журнал при кожному запуску — засмічення від демо-запусків і запусків на фікстурах;
- число текстом у цьому етапі — розширює розбір чисел; відкладено.

Outcome: `ready-for-specify`

Наступна дія: `specify` для етапу 1. Конкретне значення коду помилки, ім'я прапорця журналу, правило зіставлення міток і форму еталону для очікуваної помилки вирішує специфікація, не цей бриф.
